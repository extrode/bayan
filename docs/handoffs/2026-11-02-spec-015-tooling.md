## 1. Goal

Every script and tool in the repo becomes Bayān or shell, except where a host platform requires another language (§4). Any library code the ports need is added in its proper home (`core`, `std` or `kit`, per §6) from the start, even if that module stays incomplete.

## 3. Ground rules

- Addendum A1 still applies: nothing that changes language behavior, emitted C, goldens, `lex-diff` or 010 parity checks lands while 010–013 run. Script and CI changes land as small commits **between task merges**.
- Spec changes go through numbered revisions in `docs/revisions/`; the spec is frozen.
- New Bayān code uses current syntax: type-first declarations, no `fn`, `because "…"` as a clause (not `because:`), plain parameters (not `in`), particles at most once per signature, naming grammar per GRAMMAR.md (fallible pairs `parse`/`tryParse`, `-ed` copies, no `toX`/`asX`, codecs as static `encode`/`decode`).
- Public functions declare `uses`; I/O goes through the matching effect (`fs`, `env`, `process`, `net`, `console`, `clock`, `random`). Data read from outside is `Untrusted<T>`.
- Libraries call libc only through `rt` (K4).

## 4. What stays non-Bayān (do not port)

| Item | Stays as | Why |
| --- | --- | --- |
| Bootstrap (stage 1, `bootstrap/bayan.c`) | shell + C | must run before any `bayan` exists |
| Pinned-build fetch/cache step | shell | produces the `bayan` everything else uses |
| VS Code extension | TS/JS | VS Code only loads JS |
| Visual Studio provider | C# | Visual Studio SDK |
| `upload-artifact`, `download-artifact` | GitHub actions | no supported shell equivalent |
| C# compiler and its tests | C# | replaced by self-hosting (010–012), not 015 |

Tests and generators around editor tooling (`npm run lsp`, `npm run grammar`, `tests/lsp-regress.js`) **are** candidates.

**Shell vs Bayān:** shell (`sh`/`bash`, `set -euo pipefail`, ShellCheck-clean) for glue, sequencing other tools, environment setup, and anything that must run without `bayan`. Bayān for parsing (JSON, XML, text formats), data transformation, hashing, decisions over structured data, or anything past roughly 50 lines of shell. Bayān tools are scripts (`bayan run tools/<name>.byn`) unless shared, then a small package under `tools/`.

## 5. Work now (before 010 lands)

### 5.1 CI actions (T4) — one commit between merges

- Replace `actions/checkout` with a shell step: `git init`/`fetch` of the exact `GITHUB_SHA`, explicit fetch depth (full history only where a job needs it), auth via `GITHUB_TOKEN` header if the repo is private.
- Replace `actions/setup-dotnet` with `dotnet-install.sh` **verified by SHA-256** (pin the script hash in the workflow, or vendor the script in the repo). Never pipe a live download into a shell. Pin the SDK version as today.
- Keep `upload-artifact`/`download-artifact` at their current pinned versions.
- Verify: the workflow passes on a branch, and the job logs show the same SDK version and commit as before.

### 5.2 Pinned build for gates (T2) — one commit between merges

- A shell helper (e.g. `tools/pinned-bayan.sh`) resolves the last merge commit on `dev`, builds `bayan` from it into `.cache/bayan/<sha>/` if missing (use a worktree; never touch the caller's tree), and prints the binary path.
- `guard.sh`, `land.sh` and every tooling script that invokes `bayan` call it through the helper.
- If the pinned build fails, exit non-zero with the commit and the build log path. **Never fall back to the working tree.**
- The pin follows `dev` automatically; nobody edits it by hand. The compiler's own tests keep using the working tree.
- `.cache/` is git-ignored. Document the helper in HANDOFF.md.

### 5.3 Write `docs/specs/015-tooling/015-spec.md`

1. **Inventory.** Find every non-Bayān, non-C# file and tool: by extension (`.py`, `.js`, `.mjs`, `.cjs`, `.ts`, `.sh`, `.ps1`, …), by shebang, `package.json`/`deno.json`/`requirements*.txt`/`pyproject.toml`, and every step in `.github/workflows/`. Include the revision 0015 Unicode-table generator.
2. **Classify each** as Keep (with the §4 reason), Shell, or Bayān.
3. **For each Bayān port, list the APIs it needs** and the module each comes from (§6). Mark each API as Exists (v0.1 builtin), Spec-only, or New.
4. **Order the ports** easiest first, grouped so each new API is introduced by the first port that needs it.
5. **List the spec questions** for every New public API (signature, module, effects, failures) for the user to approve.
6. **Parity plan per port:** how old and new outputs are compared (same inputs, byte-for-byte or normalized diff).

Hand the spec to the user before `/tasks`.

## 6. Placement for the needs known so far

| Need | Home | Note |
| --- | --- | --- |
| Environment variables, args | `std.env` | `std.cli` struct-derived parsing later; keep call sites in that shape |
| exists / mkdir / remove / rename / glob / walk / temp | `std.fs`, `std.path` | capability `Dir` handles are the target design |
| Spawn, exit codes, pipes | `std.process` | `run` exists (`uses process`) |
| Print, stderr | builtins | `print(…, to: .stderr)`, `uses console` |
| JSON | `std.json` | reading needs decoders, spec-only in v0.1: raise this first |
| Regex | `std.regex` | |
| SHA-256 | `std.crypto` | hashes are `std` regardless of Q2 |
| Hex | `Hex` codec | v0.1 builtin |
| Base64 | `Base64` codec | spec-only; module name Open (Q3) |
| XML (.trx, Cobertura) | `kit.xml` (new) | pull reader only; no DTDs, five predefined entities, no external entities; output `Untrusted` |
| HTTP(S) | `kit.http` over `kit.tls` | not before `kit.tls`; until then shell out to `curl` via `std.process` and record a todo |
| Unicode data parsing | `std.fs` + `core` string members | tables' home Open (Q4) |
| Timing, durations | `std.time` | `uses clock` |

Anything not in this table: look it up in the companion doc's catalogs (§4–§6 there). If it is not there either, stop and ask.

## 7. Work after 010 lands: porting loop

For each script, in the order from 5.3:

1. Confirm its APIs are approved (spec questions answered).
2. Add missing APIs in their module, with tests (`std.test`), doc comments, effects declared, grammar checker clean. Implement only what this port needs.
3. Write the port; run it under the pinned `bayan`.
4. Run the parity check against the old script on the recorded inputs.
5. Switch callers (CI, other scripts, docs) to the port, and delete the old script **in the same commit**.
6. When the last script needing a runtime (Node, Python, Deno) is gone, remove that runtime from CI and from the dev setup docs.

## 9. Done when

- No `.py`, `.js`/`.ts` (outside the VS Code extension), Deno or other non-Bayān tooling remains except the §4 list.
- CI installs no Node, Python or Deno runtime of its own; only the two artifact actions use Node.
- Guard and land run the pinned build.
- Every library API added lives in the module the companion doc names, with tests.
- `docs/specs/015-tooling/015-spec.md` records each port with its parity result.
