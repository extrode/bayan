# 0015 — `f32.tryParse` / `f64.tryParse`; Unicode `lowercased()` / `uppercased()`

Status: accepted 2026-10-31 (user decision, for spec 010 T17).

## Problem

1. **Text to float.** SPEC §6.2's conversions table reads text into integers only (`u64.tryParse(text)`), and §16.4's conversions name `T.tryParse(text)` without saying which `T`. There is no way to read a float from text, which the self-hosted compiler needs for float literals and programs need for numeric input.
2. **Case mapping.** §16.4 says `lowercased()` and `uppercased()` use Unicode's invariant mappings, but its v0.1 scope line ships them ASCII-only, so `"ÉTÉ".lowercased()` is `"éTé"`.

## Decision

1. **`f32.tryParse(text)` and `f64.tryParse(text)`** join the `tryParse` family and return `f32?` / `f64?`. They take no `as:`.
   - The accepted text is the Bayan float literal form without `_` separators: an optional leading `-`, one or more decimal digits, an optional fraction (`.` and one or more digits), an optional exponent (`e` or `E`, an optional `+` or `-`, one or more digits). A plain integer (`"42"`) is accepted.
   - `null` for anything else: leading or trailing whitespace, a leading `+`, `1.` or `.5`, hex floats (`0x1p3`), `inf`, `infinity`, `nan`, empty text, partial text (`1e`, `1e+`, `-`, `.`), and `_` (`1_000.0`). Like the integer `tryParse`, no locale is consulted: the separator is always `.`.
   - The result is correctly rounded (round to nearest, ties to even) from the exact decimal value, at the target's precision: `f32.tryParse` rounds once to `f32`, never through `f64`.
   - Overflow is not an error: a value beyond the largest finite magnitude gives `+∞` or `-∞`, as .NET Core 3.0+ `double.Parse` does. Underflow rounds to the nearest representable value, a subnormal or `±0`. `"-0"` is `-0.0`.
2. **`lowercased()` uses Unicode simple case mapping**: each code point maps to its UnicodeData.txt field 13 (simple lowercase) mapping, or itself, as .NET's `ToLowerInvariant` does. No context: there is no final-sigma rule (`"ΣΑΣ".lowercased()` is `"σασ"`), and no one-to-many mapping (`"İ"` stays one code point). The one exception, matching .NET's invariant casing on every platform, is U+0130 `İ`, which maps to itself rather than to `i`. The table follows the Unicode version of the .NET runtime the compiler is built with (16.0.0 for .NET 10).
3. **`uppercased()` makes the same change**, since it is the same table read from field 12 (simple uppercase): `"ß".uppercased()` stays `"ß"`, `"ǅ".uppercased()` is `"Ǆ"`. Its exception is U+0131 `ı`, which maps to itself rather than to `I`, again as .NET's `ToUpperInvariant` does.
4. A mapping can change the byte length of the text (`"Ⱥ"`, 2 bytes, lowercases to `"ⱥ"`, 3 bytes); both members still allocate one new string. `equals(as: .caseless)` stays ASCII-only until `std.text`.

**Float literals today, recorded and unchanged.** The lexer takes `1e400` as a float literal with no diagnostic (it checks the shape only: digits, an optional `.` followed by a digit, an optional exponent). The binder reads it with `double.Parse(text, NumberStyles.Float, CultureInfo.InvariantCulture)` after removing `_`, which gives `+∞`; the C emitter writes `((double)INFINITY)`. With the suffix `f` or an `f32` target the value is narrowed from that `double`. So `1e400` is `inf` at compile time, the same value `f64.tryParse("1e400")` gives at run time. This revision does not change it.

## Sūq files

None affected: no Sūq source reads floats from text or calls `lowercased()` / `uppercased()` on non-ASCII text.
