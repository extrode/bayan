## Approach

**A function type is a structural `ConstructedType`; a function value is a (code, environment) pair that borrows the frame that made it.** `FunctionType(Parameters, Return, Fails, Uses)` joins `OptionalType`, `SpanType`, `TupleType` and the rest in `Types.cs` (ConstructedType at :162 gives structural `Equals`/`GetHashCode` through `Key`), with `IsBorrow => true` (Types.cs:35, as `SpanType` at :183). That one bit buys R10 for free: region analysis already forbids storing a borrow in a field (BYN3001), returning it (BYN3003, RegionAnalysis.cs:449) or outliving its source (BYN3002, :436), and reports modification while borrowed (BYN3004, :506). In C the value is `struct { R (*fn)(void* env, A, B[, R* out]); void* env; }`, emitted through `Named`/`EmitTypes` like a tuple (CEmitter.cs:254, :262-306); a call through it is `f.fn(f.env, …)`.

**Lambdas are lifted to ordinary `FunctionSymbol`s at bind time; captures are tuple fields.** A lambda binds to a synthesized `FunctionSymbol { Kind: FunctionKind.Lambda, Module, File, Parameters from the expected type, ReturnType, ErrorSets, Fails }` appended to `ModuleSymbol.AllFunctions` (Symbols.cs:56), so lowering (Lowerer.cs:19), the analyses loop (Compilation.cs:914-932), `bayan types` (TypedDump.cs:27) and emission (CEmitter.cs:61) see it with no new loop. The body is bound inline by the enclosing binder with `_fn` switched to the lambda symbol and a nested scope, so `return` targets the lambda and outer names resolve through `_scope.Lookup` (BinderExpressions.cs:408); a resolved outer local is recorded as a capture. The bound expression `BoundLambda(Syntax, Lambda, Captures: BoundLocal[], Type)` lists one `BoundLocal` read per capture as its children (BoundTree.cs:7), so flow analysis sees a read, ownership analysis sees a copy (BYN2780 for `unique`, OwnershipAnalysis.cs:407) and region analysis sees a value derived from every capture's root (RegionAnalysis.cs:517, :537), with no lambda-specific rule in any of the three. Lowering spills the captures into a temp of type `TupleType(captures)` (Lowerer.cs:88 `NewTemp`, Types.cs:271) and builds the pair from the lifted function's name and `&temp`; inside the lifted function the emitter maps each captured `LocalSymbol` to `((tuple*)env)->itemN` through `_names` (CEmitter.cs:775-778), so the body reads captures as if they were locals. Tuples already have C definitions (:304), keys (:250) and equality, so no new type emission is needed for environments. The temp lives for the whole enclosing frame (locals are declared at function top, :806-809), which is longer than any borrow of the lambda can be (R10). Rationale over monomorphizing the callee per lambda (spec §3.16's "inlined"): one calling convention serves named functions, non-capturing and capturing lambdas alike, the generics machinery is untouched, and inlining stays a later optimisation that changes no observable behaviour (L013 pins that).

**Named functions as values reuse the `BoundMethodGroup` hook.** `Binder.cs:959-966` already recognises a module function named as a value and renders its signature for a mismatch. Conversion to a function type moves that check into `Conversions.Implicit` (Conversions.cs:11) as `ConversionKind.ToFunction` over a `BoundMethodGroup { Receiver: null, Function: { Kind: Function, !IsGeneric } }` (particles are part of the name, not of the type, so a function with particle-labelled parameters qualifies; round 3 §15), producing `BoundFunctionRef(Function, Type)`; the emitter wraps the function in a per-function thunk with the `void* env` first parameter. `Panic.onPanic` keeps its path untouched (Q114).

**Calls through a value are `BoundCall`s of a synthesized invoke symbol.** Per `FunctionType` the compilation holds one `FunctionSymbol { Kind: FunctionKind.Invoke, Parameters: unnamed, ReturnType, ErrorSets, Fails }`; `BindCall` (BinderCalls.cs:24) adds a case for a callee whose type is a `FunctionType` and goes through `BindFunctionCall` (:73) with the value as `Receiver`. Everything downstream that keys on `BoundCall` keeps working: the `fails` check and `try` insertion (:100-105), `ErrorFlow` (ErrorFlow.cs:15, :18), the try/catch lowering, and `BoundTree.Children`. Two places must learn that a receiver without `HasThis` is the callee value: `Lowerer.CallParts` (Lowerer.cs:1124 drops the receiver unless `HasThis`) and `CEmitter.Call` (CEmitter.cs:1175). Round-3 step 5.3e's particle matching sees an invoke symbol's parameters as unlabeled and unnamed, so a labelled argument falls into the existing missing-parameter path.

**`it` is a binder decision, not a parser one.** The parser never sees `it`; `BindArgumentValue` (BinderCalls.cs:351) checks, when the parameter type is a one-parameter `FunctionType` and the argument is not a `LambdaExpr`, whether the argument's syntax mentions the name `it` outside a nested `LambdaExpr`, and if so binds it as a lambda whose one parameter is named `it`. A depth counter makes a second such argument inside the first BYN2029; the counter starts at one inside a `requires` rule (round 3 §11, bound by step 5.3b), where `it` already names the checked value (Q130). `.name` with an expected function type is caught in `BindTargetMember` (BinderCalls.cs:26 passes `expected`) and reported as BYN2823.

**Effects ride on the type; checking waits for round-3 step 5.3d.** `FunctionType.Uses` is resolved from the `uses` list round-3 step 5.1d parses for functions, compared in `Key` (R3) and shown in `DisplayName`. Function-typed parameters are effect-polymorphic (round 3 §13: a function taking a closure inherits its effects): a call through a parameter charges nothing to its function, and a call that passes a `BoundFunctionRef` or `BoundLambda` to a function-typed parameter charges that argument's effects to the caller (a forwarded parameter charges nothing). Elsewhere (a local, Q128) the conversion checks the effects against the type's `uses` bound (BYN6005, round 3) and a call through the value charges that `uses`. All of it hooks into 5.3d's effect pass (a new file per the round-3 plan) and lands with whichever of 007 T4/T5 and 5.3d comes second.

## Risks & mitigations

- **Two-pass binding of bodies** (Compilation.cs:1103-1133): the first `BindBody` lifts lambdas into `AllFunctions` and the second lifts them again. Mitigation: record lambdas lifted during a pass in the same `pass` tuple as instances and remove them at :1125; a golden with a lambda inside a function that has an untyped-literal `var` (the rollback trigger, `run/generics-var-literal-rollback.byn`'s shape) proves it.
- **`=>` after a type**: `=>` after a type is a function type's input form in some positions and an expression body in others (`bool isBig(i32 x) => x > 2`, `bool isEmpty => lines.isEmpty`). Mitigation: `ParseType` takes a flag from its caller saying whether a body may follow; return types and field types (which now precede the name, so `=>` follows the parameter list or field name) pass it and never see BYN1055; parse goldens for both, recorded as Q121.
- **Statement-start speculation**: with round-3 5.1b, locals start with `let`/`var` and the C#-style `T name =` shape is only scanned to report BYN1043. `(a, b) => …` at statement start must not scan as a tuple type followed by a name. Mitigation: `ScanType`'s paren path returns -1 when the closing `)` is followed by `=>` and the elements are bare names; parse goldens for both statement shapes.
- **`fails`/`uses` lists inside a function type** (`(() -> Token fails A, B) next`): a function-typed parameter is parenthesized (J54), so in a parameter list the list ends at the closing `)`. In a type argument, a tuple element or a function type's own parameter list, `, B` stays ambiguous. Mitigation: there, the list takes one name unless parenthesised (`fails (A, B)`); recorded as Q121.
- **Tuple of one capture**: `TupleType` with a single field is never produced by the parser; the symbol and emitter accept any count (Types.cs:271, CEmitter.cs:304-305), but `Key` "tup1_x" and equality helpers were never exercised. Mitigation: T7 adds a run golden with exactly one capture; if anything balks, the environment pads with a `bool`.
- **Environment temp per evaluation**: a lambda created in a loop reuses one temp, so a lambda value from iteration *i* held past iteration *i+1* would see new captures. Region analysis forbids that only if the lambda value borrows the temp. Mitigation: the lowered `LFunctionValue` reads the env temp as a `BoundLocal`, and `FunctionType.IsBorrow` plus the loop-scope region rules make a function value that escapes its iteration BYN3002; L014's table includes this shape.
- **Capturing a narrowed value** (BinderExpressions.cs:412-413 wraps a non-null `let` in a `Narrow` conversion; round-3 5.3c adds state refinements `T is .s`): the capture must copy the narrowed value, not the optional, and keep a state refinement. Mitigation: captures record the `BoundLocal` read exactly as `BindName` produced it; the tuple field has the narrowed type.
- **Effects lowering** (round-3 5.3d, "handlers compile to context passing"): if `provide` handlers become hidden parameters of effectful functions, a call through a `uses` function value must pass them. Mitigation: 007 does not choose; T7 makes the `fn` pointer's signature come from the same `Signature` path as named functions, and whichever of T7 and 5.3d lands second adds the hidden parameters there, with a run golden of a `uses` function type.
- **`-Wall -Werror` on pre-existing emission**: 006 T11 cleaned pre-existing emission; 007 fixes only new warnings from lambda emission and records any narrowing in its proof notes.
- **`it` detection by syntax walk** runs on every argument to a function-typed parameter; it is linear in the argument's size and only when the parameter type is a one-parameter function type, so no measurable cost. A `NameExpr` named `it` that resolves to a user local named `it` is still rewritten; Q117 records that a local named `it` cannot be passed bare to such a parameter (write a lambda with a named parameter instead).
- **Lambdas inside generic templates** are bound once on the template (ownership runs there) and once per instance (flow, regions); the lifted symbol must exist per instance with substituted types. Mitigation: the lambda is lifted during the binding that creates it, so each instance's `BindBody` creates its own; `FunctionName` adds the instance's `TypeArgs` (CEmitter.cs:181).
- **Goldens of `.ast` dumps**: new node kinds change no existing dump; `parse/` additions only.

## Self-hosting gaps

What spec 009's port must work around, given this subset:
- No stored callbacks: a visitor table, a `Dictionary<TokenKind, Func<…>>` or a parser rule table becomes a `switch` or a function-typed parameter threaded through the calls.
- No function-typed fields or return types: a "parse this then that" combinator style is out; helpers take their callback as a parameter each call.
- No `ref` captures: a lambda that must update a counter takes it as a `ref` parameter of the called function instead, or the loop is written out.
- No built-in `where`/`select`/`sort(by:)`: the port writes `any`, `indexWhere`, `sortBy` over spans once in its own prelude.
- No generic aliases: `type Predicate<T>` is spelled per type (`type TokenPred = Token -> bool`).
- No effect variables: a function-typed local that may use an effect declares it in its type (`let hook: string -> string uses fs = …`); parameters need nothing (they inherit their argument's effects).
- No lambdas in `const` initializers and no function values in `static` data: keyword tables stay arrays of names, not of handlers.
- No `this` capture: a method that passes a lambda copies the fields it needs into `let` values first.
